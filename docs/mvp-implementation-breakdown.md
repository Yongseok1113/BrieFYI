# MVP 구현 항목 분해표

설계 문서(1단계 MVP: 배치 트리거 + GNews 수집 + 단일 요약 + 이메일 발송)를 실제 개발 가능한 단위로 쪼갠 표다. 위에서 아래로 대체로 구현/실행 순서와 일치한다.

## 1단계 MVP (반드시 구현)

| # | 구현 항목 | 기능 설명 | 입력 | 출력 | 선행 의존성 | 추천 기술스택 |
|---|---|---|---|---|---|---|
| 1 | 뉴스 수집 모듈 | GNews API 호출, 키워드/기간으로 기사 목록 조회 | 키워드, 기간, 카테고리 | 기사 리스트(JSON) | 없음 | Python + requests, GNews API key |
| 2 | 원시 데이터 저장 | 수집 결과를 재사용/감사 가능하게 저장 | 기사 리스트 | 저장된 raw 데이터 | 1 | SQLite 또는 로컬 JSON 파일(MVP 단계는 과설계 지양) |
| 3 | 요약 생성 | 기사별/묶음별로 LLM 요약 호출 | raw 기사 | 요약문 | 2 | Claude API, 구조화 출력(JSON mode) |
| 4 | 인사이트+시사점 생성 | 요약을 종합해 핵심 인사이트 3~5개, 비즈니스 시사점 도출 (MVP는 요약과 한 프롬프트로 합쳐도 무방) | 요약문 | 인사이트/시사점 JSON | 3 | 동일 Claude API 호출, 프롬프트 체이닝 |
| 5 | 이메일 포맷터 | 구조화된 JSON을 이메일 HTML로 변환 | 인사이트 JSON | HTML 본문 | 4 | Jinja2 템플릿 |
| 6 | 이메일 발송 | 완성된 콘텐츠를 수신자에게 발송 | HTML 본문, 수신자 목록 | 발송 성공/실패 결과 | 5 | Resend 또는 SendGrid API (SMTP도 가능) |
| 7 | 오케스트레이션 스크립트 | 1~6을 순서대로 호출하는 메인 실행 로직 | 실행 파라미터 | 파이프라인 실행 결과 | 1~6 | 단일 Python 스크립트(에이전트 프레임워크 없이도 가능) |
| 8 | 스케줄 실행 | 매일 정해진 시각에 7을 자동 실행 | 없음 | 정기 실행 | 7 | cron, GitHub Actions 스케줄, 또는 Cowork 스케줄 작업 |

MVP는 "에이전트가 자율적으로 판단"하기보다 정해진 순서대로 도구를 호출하는 고정 파이프라인으로 시작하는 것을 권장한다. 파이프라인이 안정화된 후에 오케스트레이터를 에이전트화(재시도, 소스 선택 등을 LLM이 판단)해도 늦지 않다.

## 2단계 이후 (MVP 검증 후 백로그)

| # | 구현 항목 | 기능 설명 | 선행 의존성 |
|---|---|---|---|
| 9 | Discord 발송 모듈 | Discord Webhook으로 동일 콘텐츠 발송 | 4 (인사이트 JSON), 6과 병렬 구현 가능 |
| 10 | 검증/품질게이트 | 인사이트가 원문 근거와 일치하는지 확인, 미달 시 재작업 | 4 |
| 11 | 기술문서 수집 모듈 | 빅테크 블로그/RSS 크롤링 | 1과 병렬, 2에 합류 |
| 12 | 중복제거/클러스터링 | 임베딩 기반 유사 기사 그룹화, 다이제스트 간 중복 방지 | 2, 벡터 저장소 필요 |
| 13 | 실시간 트리거 경로 | 짧은 폴링 주기 또는 웹훅으로 긴급 이슈 즉시 처리 | 1, 3 (간소화된 버전) |
| 14 | 개인화/피드백 루프 | 수신자별 관심 주제 반영, 반응 학습 | 6, 9, 배포 이력 로그 |
| 15 | 대시보드 | 축적된 인사이트 검색/열람 | 가공 결과 DB |

## 구현 순서 원칙

같은 단계 내에서는 수집(1) → 저장(2) → 분석(3~4) → 포맷팅(5) → 발송(6) → 실행 자동화(7~8) 순으로 의존성이 명확하므로 이 순서를 벗어나기 어렵다. 반면 9번(Discord)과 11번(기술문서 수집)은 MVP 파이프라인과 독립적으로 병행 개발이 가능하니, 일손이 여유 있다면 동시에 진행해도 된다. 10번(검증)은 3~4번 프롬프트 품질을 먼저 눈으로 확인한 뒤 필요성을 판단해 착수하는 편이 효율적이다.
