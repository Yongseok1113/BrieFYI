# GNews 기반 "인사이트 추론" 파인튜닝 — 학습 데이터 & 골드셋 설계

- 대상 모델: Qwen3-8B, QLoRA (제공된 `qlora_qwen3_8b_colab.ipynb` 기준, Colab T4)
- 목표 능력: 여러 뉴스 기사를 묶어(clustering) 그 이면에 있는 함의·전략적 의도·리스크/기회를 추론하는 능력
- 정답 생성자: Claude (본 세션), 학습/평가는 Qwen3-8B LoRA

> **가정 확인**: 원문에서 "3b에 학습 데이터를 lora로 학습"이라고 하셨는데, 첨부하신 노트북 파일명과 내용이 명확히 `Qwen3-8B`(`qwen3_8b`, `qlora_qwen3-8b.yaml`)를 가리키고 있어, 본 문서는 **Qwen3-8B**를 대상으로 설계했습니다. 만약 실제로 Qwen3-**1.7B**나 다른 경량 모델로 먼저 빠르게 이터레이션하고 싶으신 의도였다면(노트북에도 "스모크 테스트" 경로가 있는 걸 보면 가능성 있음), 데이터 구성 방식은 동일하고 `configs/`의 base_model만 바꾸면 되므로 이 문서의 전략은 그대로 재사용 가능합니다.

## 1. 문제 정의: "인사이트 추론"이란 무엇인가

단순 요약(summarization)과 구분되는 이 태스크의 핵심은 **"기사에 명시적으로 쓰이지 않은, 그러나 기사들을 종합하면 합리적으로 도출되는 함의"**를 생성하는 것입니다. 학습 데이터 설계 전에 이 능력을 다음 6가지 하위 유형(taxonomy)으로 분해해서, 데이터가 특정 유형에 치우치지 않도록 관리합니다.

| 유형 | 설명 | 예시 신호 |
|---|---|---|
| 전략적 의도 추론 | 발표된 행동(투자, 채용, 파트너십) 뒤에 있는 전략을 추론 | "A사가 B사와 독점 공급계약" → 경쟁사 견제 의도 |
| 모순/긴장 탐지 | 같은 사안에 대한 여러 소스 간 진술 불일치, 또는 말과 행동의 불일치 | 공식 발표는 "협력 강화"인데 동시에 인력 감축 기사 |
| 선행지표 포착 | 개별로는 사소하지만 반복되면 트렌드가 되는 신호 | 3주간 동일 기업 관련 "공급 지연" 기사 3건 |
| 이해관계자 영향 분석 | 이 사건이 다른 행위자(경쟁사, 고객, 규제기관, 투자자)에 미치는 파급 | 반도체 수출규제 → 특정 스타트업들의 GPU 조달 리스크 |
| 시장 신호 해석 | 인사·조직 개편, 특허, 채용공고 등 간접 신호로 방향성 해석 | 특정 직군 채용 급증 → 신사업 진출 신호 |
| 리스크/기회 도출 | 독자(팀/조직) 관점에서 실질적으로 취할 수 있는 시사점 | "이 규제는 국내 스타트업엔 오히려 기회일 수 있다" |

이 taxonomy는 3절(프롬프트 설계), 5절(분할), 7절(평가 루브릭)에서 반복적으로 참조합니다.

## 2. GNews API 수집 전략

### 2.1 API 제약 조건 (설계에 직접 영향)

Free 플랜 기준(2026년 8월 현재, [gnews.io/pricing](https://gnews.io/pricing)):

- **요청 100회/일**, 요청당 최대 **10건**, 최대 **100건/일** 실질 수집
- **12시간 지연** 발행(실시간 아님), **최근 30일** 기사만 검색 가능
- `content` 필드는 **truncate(잘림)** — 본문 전체 아님, `description`(요약) + `content` 일부만 사용 가능
- 검색 파라미터: `q`(최대 200자, AND/OR/NOT 지원), `lang`, `country`, `in`(title/description/content), `from`/`to`(ISO8601), `sortby`(publishedAt/relevance), `max`(free는 최대 10)

이 제약이 의미하는 것: **하루 100건 안팎의 예산으로 "많은 기사를 얕게" 긁는 대신, 클러스터링이 잘 되도록 "적은 이벤트를 여러 소스로 두껍게" 모으는 전략이 유리**합니다. Essential 플랜(월 €49.99, 1,000req/일, 실시간, 전체 content)으로 업그레이드하면 이 제약 상당수가 풀리므로, 학습 데이터 규모를 키우는 시점(5절 참고)에는 유료 전환을 권장합니다.

### 2.2 쿼리 설계: 2단 구조 (시드 엔티티 × 이벤트 유형)

**시드 엔티티 세트** (프로젝트 설명에 명시된 대상 기반):
- 빅테크: NVIDIA, OpenAI, Anthropic, Google DeepMind, Google, Microsoft, Meta AI, TensorFlow, PyTorch
- 확장 후보: TSMC, ASML, AMD, xAI, Mistral, Hugging Face, AWS/Amazon (경쟁·공급망 맥락 없인 인사이트가 안 나오므로 최소 이 정도 확장 필요)

**이벤트 유형 필터** — "인사이트가 나올 확률이 높은" 기사 유형을 우선 수집 (무작위 뉴스는 클러스터링해도 표면적 사실 나열에 그치기 쉬움):
- 투자/M&A/펀딩 (`funding round`, `acquisition`, `investment`)
- 인사 변동 (`executive departure`, `hires`, `resigns`)
- 규제/소송 (`antitrust`, `lawsuit`, `export control`, `regulation`)
- 파트너십/공급계약 (`partnership`, `supply deal`, `exclusive agreement`)
- 제품/모델 출시 (`launch`, `release`) — 다만 이건 인사이트보다 사실 요약에 가까우므로 비중은 낮게

쿼리는 `q="NVIDIA" AND ("acquisition" OR "lawsuit" OR "export control")` 식으로 **엔티티 × 이벤트유형** 조합을 만들고, 요청 예산(100/일) 내에서 로테이션합니다. 예: 하루 8~10개 조합 쿼리 × 요청당 10건 = 80~100건.

### 2.3 의도적으로 "평범한" 기사도 일부 포함

인사이트 추론 모델이 모든 입력에 대해 억지로 그럴듯한 추측을 만들어내는 것(환각/과잉해석)을 막기 위해, 전체 수집량의 **약 15~20%는 특별한 함의가 없는 단발성 사실 기사**(제품 스펙 발표, 일상적 실적 발표 등)로 의도적으로 채웁니다. 이는 5절의 "무(無)인사이트" 골드 라벨과 짝을 이룹니다.

### 2.4 수집 스케줄 & 캐싱

- 일 1회 배치(기존 다이제스트 파이프라인과 동일 주기)로 쿼리 로테이션 실행
- `(query, from, to)` 키로 결과 캐싱 → 동일 기간 재요청 방지 (일 100회 예산 보호)
- 각 기사 저장 필드: `title, description, content(truncated), url, image, publishedAt, source.name, source.url, query_tag(어떤 시드/이벤트유형으로 수집됐는지)` — `query_tag`는 4절 클러스터링과 6절 분할 시 근거 추적에 씀

## 3. 기사 연관관계(클러스터링) 알고리즘

목표는 "같은 사건/테마를 다루는 기사 묶음"을 만드는 것이며, 정확도보다 **재현율(recall)을 약간 높게** 잡는 편이 낫습니다 — 인사이트는 오히려 "약하게만 연결된" 기사 사이에서 나오는 경우가 많기 때문입니다(5절 참고). 4단계 파이프라인을 제안합니다.

**1단계 — 시간창 필터**: `publishedAt` 기준 롤링 윈도우 두 개를 병행 운영
- 좁은 윈도우(48~72시간): "같은 사건"을 다루는 기사 클러스터용
- 넓은 윈도우(2~4주): "같은 테마의 흐름"을 다루는 클러스터용 (예: "N사 공급 이슈"가 3주간 반복 등장 → 선행지표형 인사이트 재료)

**2단계 — 엔티티 오버랩**: title+description에서 회사명/인명/제품명 추출(간단 키워드 매칭 + 필요시 경량 NER)하여 자카드 유사도로 1차 후보 그룹 생성. 한/영 혼용 대응을 위해 별칭 사전 사용(`엔비디아`↔`NVIDIA`, `오픈AI`↔`OpenAI` 등) — 프로젝트가 한국어 AI 뉴스도 다루므로 필수.

**3단계 — 임베딩 기반 정제**: title+description을 임베딩(예: multilingual-e5 계열)하여 코사인 유사도 계산, HDBSCAN 또는 계층적 클러스터링으로 2단계 후보군을 정제·병합. 순수 임베딩 유사도만 쓰면 "같은 회사 언급"만으로 묶이는 오탐이 많으므로 반드시 2단계와 결합.

**4단계 — LLM 검증/병합 (Claude)**: 최종 후보 클러스터를 Claude에게 "이 기사들이 정말 같은 사건/테마를 다루는가? 다르면 어떻게 나눌 것인가?"로 재확인시켜 최종 확정. 이 단계가 3절 골드 생성과 자연스럽게 이어지므로, 실제로는 **클러스터 검증과 인사이트 생성을 하나의 Claude 호출 파이프라인으로 묶는 것**을 권장(비용 절감 + 일관성).

**클러스터 스키마 예시**:
```json
{
  "cluster_id": "c_2026-08-15_nvidia_supply",
  "window_type": "narrow | broad",
  "articles": [
    {"title": "...", "description": "...", "source": "...", "publishedAt": "...", "url": "...", "query_tag": "..."}
  ],
  "entities": ["NVIDIA", "TSMC"],
  "event_type": "supply_chain"
}
```

## 4. 골드/학습 데이터 구성 — Claude를 정답 생성자로

### 4.1 출력 스키마 (구조화)

모델이 "사실"과 "추론"을 혼동하지 않도록, 학습 타깃 자체를 구조화된 스키마로 만듭니다.

```json
{
  "facts": ["기사들에서 직접 확인되는 사실 1", "..."],
  "insights": [
    {
      "claim": "추론된 인사이트 문장",
      "type": "전략적_의도 | 모순_긴장 | 선행지표 | 이해관계자_영향 | 시장_신호 | 리스크_기회",
      "evidence": ["근거로 쓴 사실 인덱스 또는 기사 url"],
      "confidence": "high | medium | low",
      "reasoning": "사실→추론으로 이어지는 1~2문장 논리"
    }
  ],
  "no_strong_insight": false
}
```

`no_strong_insight: true`인 경우(4~5절의 "평범한 기사" 클러스터) `insights`는 빈 배열 또는 매우 낮은 confidence만 허용 — 이게 바로 모델이 "억지 추론"을 하지 않도록 잡아주는 캘리브레이션 라벨입니다.

### 4.2 프롬프트 설계 (2-pass: 초안 → 자기검증)

**Pass 1 (생성)**: 클러스터의 기사 목록을 주고, 위 스키마로 출력하도록 요청. 이때 taxonomy 6종 중 최소 2종 이상을 시도해보게 유도(다양성 확보), 억지로 6종을 다 채우진 않게 함.

**Pass 2 (검증/가지치기, 별도 호출)**: Pass 1 출력을 다시 Claude에게 주고 "각 insight가 주어진 기사만으로 합리적으로 도출되는가, 아니면 기사에 없는 외부 지식/추측에 의존하는가?"를 판정 → 근거 부족한 insight는 제거하거나 confidence를 낮춤. 이 2-pass가 없으면 "그럴듯하지만 실제로는 기사 밖 지식으로 채운" 환각성 라벨이 섞여 들어갈 위험이 큽니다(Claude 자신이 배경지식으로 채워넣는 경향).

### 4.3 사람 검수 샘플링 (필수)

Claude가 생성자이자 (궁극적으로) 검증 기준이 되므로, 자기 확증적 오류가 학습 데이터에 체계적으로 스며들 위험이 있습니다. 최소한:
- 학습셋: 랜덤 5~10% 샘플을 사람이 직접 검토, "사실 오류/과잉해석/근거부족" 여부 체크
- 골드셋(테스트): **전수 또는 최소 30~50%**를 사람이 검토 — 평가 기준 자체가 틀리면 이후 모든 평가가 무의미해지므로 골드셋 품질 기준은 학습셋보다 훨씬 엄격해야 함

검수에서 반려율이 특정 임계치(예: 15%)를 넘는 카테고리가 있으면 해당 유형의 프롬프트를 재설계.

## 5. Train / Val / Gold(Test) 분할 전략

- **시간 기준 분할** (랜덤 분할 금지): 예) 8/1~8/20 클러스터 → train, 8/21~8/25 → val, 8/26~8/31 → gold test. 실제 배포 시나리오(과거 데이터로 학습, 미래 사건에 대해 추론)를 모사하고, 같은 사건이 train/test에 동시에 들어가는 leakage를 원천 차단.
- **클러스터 단위 분리**: 개별 기사가 아니라 클러스터 전체를 하나의 스플릿에만 배정 (한 사건이 train과 test에 걸치지 않도록).
- **규모 (노트북의 3,000건/epoch 가정과 정합)**: train 2,500~3,000 예시, val 200~300, gold test 100~150. 무료 GNews 예산(최대 ~100건/일)으로는 이 규모를 모으는 데 대략 4~6주 소요 예상 — 속도를 높이려면 Essential 플랜 전환 검토.
- **골드셋 구성 비율**: taxonomy 6종 + `no_strong_insight` 케이스가 고르게 섞이도록 층화추출(stratified sampling). 특정 유형(예: 전략적 의도 추론)에 쏠리면 평가가 왜곡됨.

## 6. 파인튜닝 실행 (제공 노트북과의 연결)

- 노트북 6절(학습 설정)의 `configs/qlora_qwen3-8b.yaml`에서 데이터 경로만 본 설계로 만든 `insight_train.jsonl` / `insight_val.jsonl`로 교체하면 바로 재사용 가능
- 프롬프트 템플릿(instruction)은 "다음 기사들을 읽고 사실과 인사이트를 JSON으로 구분해 제시하라" 형태로 고정, 4.1의 스키마를 few-shot 없이도 안정적으로 뽑아내도록 system prompt에 스키마 명시
- 학습 목표(loss)는 전체 JSON 문자열에 대한 표준 causal LM loss로 충분 — 별도 구조화 손실 불필요 (스키마 파싱 실패율은 평가 단계에서 별도 체크)
- 스모크 테스트 경로(`configs/smoke.yaml`, `data/sample/`)로 먼저 20~30건 소규모 셋으로 파이프라인 전체(수집→클러스터링→라벨생성→학습→추론)를 검증한 뒤 본 규모로 확장 권장

## 7. 평가 방법 (골드셋 기준)

세 갈래로 평가합니다.

1. **스키마/사실 정합성 (자동)**: JSON 파싱 성공률, `facts`가 실제 기사 내용과 겹치는지(ROUGE/BERTScore로 대략 체크)
2. **인사이트 품질 (LLM-as-judge, Claude)**: 골드 라벨과 모델 출력을 함께 주고 아래 루브릭으로 채점
   - 근거 충실성: 주어진 기사만으로 뒷받침되는가 (환각 여부)
   - 통찰 깊이: 표면적 재서술이 아닌 비자명한 함의인가
   - 논리적 타당성: 사실→추론 연결이 합당한가
   - 캘리브레이션: `no_strong_insight` 케이스에서 억지 추론을 안 하는가 (이 항목이 사실상 가장 중요한 차별화 지표)
3. **Base vs Fine-tuned 비교**: 같은 gold set에 대해 (a) 파인튜닝 전 Qwen3-8B(제로샷/few-shot 프롬프트), (b) LoRA 파인튜닝 후 모델을 페어와이즈로 비교 — Claude judge가 우열 판정 + 승률 집계
4. **사람 검증 서브셋**: LLM judge와 사람 평가 간 상관을 gold set의 20~30건에서 확인해 judge 신뢰도 보정

## 8. 리스크 및 완화

| 리스크 | 완화 방안 |
|---|---|
| Claude가 생성자+검증자를 겸해 자기 확증적 편향 발생 | 2-pass 생성(4.2), 사람 검수 샘플링(4.3), 골드셋은 특히 엄격 검수 |
| GNews 무료 티어(100req/일, 30일 이력, content truncate)로 데이터 부족/부실 | 이벤트유형 우선 쿼리로 효율화(2.2), 필요시 Essential 플랜 전환 |
| 모델이 모든 클러스터에 억지 인사이트를 생성(과잉해석) | `no_strong_insight` 라벨 15~20% 의도적 포함, 캘리브레이션을 평가 루브릭 핵심 지표로 |
| 클러스터링 오탐(관련 없는 기사 묶임) | 4단계 파이프라인의 마지막 LLM 검증 단계를 필수 게이트로 유지 |
| 클러스터 단위 leakage로 평가 신뢰도 저하 | 시간 기준 분할 + 클러스터 단위 스플릿 배정(5절) |

## 9. 실행 로드맵 (제안)

1. 시드 엔티티/이벤트유형 쿼리 세트 확정 → 소규모(1주) 수집 파일럿으로 클러스터링 품질 점검
2. 클러스터링 파이프라인(1~4단계) 구현 및 20~30개 클러스터로 스모크 테스트
3. 라벨링 프롬프트(4.1, 4.2) 확정 → 스모크셋 라벨 생성 → 사람 전수 검수로 프롬프트 보정
4. 본 수집 시작(4~6주, 또는 유료 플랜으로 단축) 하며 병행으로 라벨 생성
5. 시간 기준 train/val/gold 분할(5절) → 노트북으로 QLoRA 학습
6. 골드셋 평가(7절)로 base 대비 개선 확인 → 부족하면 taxonomy별 데이터 보강 후 재학습
