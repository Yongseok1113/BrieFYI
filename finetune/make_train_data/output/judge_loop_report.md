# LLM-as-Judge 기반 3라운드 프롬프트 개선 루프 (insight task, Qwen3-1.7B v3 어댑터)

> 재학습 없이, 학습이 끝난 v3 어댑터(`runs/smoke-insight-1.7b-v3-naver`, n=135 골드셋으로 학습)의
> 가중치는 고정한 채로 **추론 시 system prompt만 3번 바꿔가며** 골든 테스트셋(`insight_val.jsonl`)
> 15건 부분집합에 대해 생성 → Claude Haiku judge 채점 → 실패 패턴 분석 → 다음 프롬프트 개선을
> 반복했다. 스크립트: `judge_loop.py`, `run_round2.py`, `run_round3.py` (스크래치 경로에 있음, 이
> 리포트에 전체 내용을 옮겨 담았다). 원본 결과 JSON: `judge_loop_round{1,2,3}.json` (본 폴더).

## 0. 테스트셋

`finetune/data/processed/insight_val.jsonl`(28건, v3 학습의 held-out) 중 클래스 균형을 맞춘
**15건**(insight 있음 8 + no_strong_insight 7)을 고정 부분집합으로 매 라운드 동일하게 사용했다.

## 1. LLM-as-Judge 프롬프트 (신규 설계)

기존 코드베이스에는 요약 사실성 검증용(`GROUNDING_JUDGE_PROMPT`, finetune/evaluate.py)과 RAG 요약
종합 채점용(`JUDGE_SYSTEM_PROMPT`, rag_latest/prompts.py) 두 개가 있었지만, 둘 다 이 insight
task의 "no_strong_insight 판정이 골든셋과 맞는가 + insight 품질"을 채점하지 못했다. 이번에 새로
설계했다.

```python
INSIGHT_JUDGE_SYSTEM_PROMPT = """당신은 뉴스 기사 기반 인사이트 추출 모델의 출력을 골든 정답과
비교해 채점하는 심사자(LLM-as-a-judge)입니다. 다음 세 가지를 판단하십시오.

1. classification_match: 모델이 낸 no_strong_insight 값이 정답과 같은지(true/false).
2. grounded: 모델이 낸 facts/insights가 기사 제목·요약에 실제로 근거하는지. 원문에
   없는 사실을 지어냈다면 false로 표시하고 ungrounded_claims에 그 문장을 적으세요.
3. insight_quality(0~100): 정답이 no_strong_insight=false일 때만 평가합니다. 모델의
   insight가 정답의 insight와 방향이 비슷한 실질적 통찰인지, 아니면 사실 재진술에
   그치거나 근거 없이 억지로 만든 해석인지를 봅니다. 정답이 no_strong_insight=true면
   이 값은 null로 두세요(모델이 insight를 냈든 안 냈든, 품질 채점 대상이 아닙니다).

반드시 아래 JSON 형식으로만 답하세요. 다른 설명은 붙이지 마세요.
{"classification_match": true/false, "grounded": true/false, "ungrounded_claims": ["..."],
 "insight_quality": 0-100 또는 null, "reasoning": "한두 문장으로 근거"}
"""
```

user 프롬프트는 `# 기사(제목/요약) + # 정답(gold) + # 모델 출력` 세 블록을 JSON으로 이어붙인
것이다. Judge 모델은 `claude-haiku-4-5`(rag_latest.llm_client.call_llm, provider="anthropic")를
그대로 재사용했다 — 이 프로젝트에 이미 있는 groq/anthropic 스위처블 클라이언트를 새로 안 만들고
가져다 썼다.

## 2. 라운드별 System Prompt와 변경 이유

### Round 1 — 베이스라인 (기존 `prompt.py`의 `INSIGHT_SYSTEM_PROMPT` 그대로)

```
당신은 여러 뉴스 요약을 바탕으로 비즈니스 인사이트를 도출하는 애널리스트입니다. 근거가 충분하면
인사이트를 2~5개 도출하고(억지로 다 채우지 말고 근거가 뒷받침하는 만큼만), 각 인사이트에는 근거가
된 기사의 source_url을 반드시 포함하세요. 다만 입력이 특정 산업·시장·전략과 연결되는 구조적
함의가 없는 단발성 사실(예: 개별 사건·사고, 확정 안 된 루머)이라면 억지로 인사이트를 만들어내지
말고 insights를 빈 배열로 두고 no_strong_insight를 true로 표시하세요. 출력은 반드시 JSON이어야
합니다.
```

`max_new_tokens=400`으로 생성.

### Round 2 — "더 적극적으로 시도하라" + 정확성 규칙 초안 (Round 1 결과 반영)

Round 1에서 관찰된 것: **15건 중 4건이 max_new_tokens=400에서 JSON이 중간에 잘려 파싱 실패**
(전부 insight-보유 사례 — 인사이트가 있으면 출력이 길어져 잘리는 구조적 문제). 이건 프롬프트
문제가 아니라 생성 길이 설정 문제라 `max_new_tokens=700`으로 올렸다(프롬프트 실험과 별개의
인프라 수정으로 명확히 구분해뒀다). 판정된 11건 중: classification_match 10/11(0.909)로 이미
높았지만 grounded 7/11(0.636)로 낮았고, "Meta AI glasses" 사례처럼 명백한 신호(반발/backlash)가
있어도 모델이 인사이트 생성을 포기한 경우가 있었다.

```
당신은 여러 뉴스 요약을 바탕으로 비즈니스 인사이트를 도출하는 애널리스트입니다.

**절대 규칙**: facts와 insights의 evidence는 반드시 입력으로 주어진 제목·요약에 실제로 있는
내용만 사용하세요. 구체적인 숫자·기간(예: '3주간')·인과관계·소송 결과 예측처럼 요약에 없는
내용을 지어내지 마세요. 불확실하면 facts를 짧고 보수적으로만 적으세요.

**insight와 fact 재진술을 구분하세요**: insight는 fact를 다른 말로 반복하는 문장이 아니라, 그
fact로부터 도출한 새로운 함의(누가 영향받는지, 어떤 위험/기회가 있는지, 업계 전체에 어떤
신호인지)여야 합니다.

**단발성 사실과 인사이트 여지를 구분하는 기준**: 기업의 투자/M&A/제품 출시, 정부 정책, 소송,
시장 반응(주가·반발·논쟁) 등 구조적 함의로 이어질 수 있는 사건이 언급되면 대개 인사이트 여지가
있습니다. 반대로 개별 형사사건, 연예인 개인사, 운세·날씨 등은 no_strong_insight입니다. 판단이
애매할 때 무조건 no_strong_insight로 포기하지 말고, 근거가 약하면 confidence를 low로 낮춰서라도
인사이트를 시도하세요.

근거가 충분하면 인사이트를 2~5개 도출하고, 각 인사이트에는 근거가 된 기사의 source_url을
반드시 포함하세요. 출력은 반드시 JSON이어야 합니다.
```

`max_new_tokens=700`.

### Round 3 — "적극성" 되돌리고 정확성 규칙만 강화 (Round 2 결과 반영)

Round 2에서 관찰된 것: **grounded_rate가 오히려 0.636→0.462로 악화**, avg_insight_quality도
51.7→35.0으로 악화. "판단이 애매할 때도 시도하라"는 지시가 classification_match을
0.909→0.923으로 살짝 올렸지만, 그 대가로 숫자를 잘못 베끼거나(`1.4%`→`14%`) 없는 인과관계를
지어내는 사례가 늘었다. 그래서 이 "적극적으로 시도하라"는 지시를 빼고, 정확성 규칙만 훨씬
구체적으로(숫자 원문 그대로 인용, 기간·인과관계 검증) 강화했다. `max_new_tokens=800`(Round 2에서도
2건이 여전히 잘렸음).

```
당신은 여러 뉴스 요약을 바탕으로 비즈니스 인사이트를 도출하는 애널리스트입니다.

**정확성 규칙(가장 중요)**:
1. 요약에 나온 숫자·비율·날짜는 반드시 원문 그대로 인용하세요(예: 요약이 '1.4%'면 반드시
'1.4%'로 쓰고, '14%'처럼 다르게 옮기지 마세요).
2. 요약에 명시되지 않은 기간(예: '3주간'), 원인('~때문에'), 결과('~으로 이어질 것')를
만들어내지 마세요. 인과관계를 쓰기 전에 그 인과관계가 요약 문장에 실제로 있는지 확인하세요.
3. 확신이 없으면 facts를 짧고 보수적으로만 적으세요 — 없는 세부사항으로 채우는 것보다
짧고 정확한 것이 낫습니다.

**insight와 fact 재진술 구분**: insight는 fact를 다른 말로 반복하는 문장이 아니라, 그
fact로부터 도출한 새로운 함의(누가 영향받는지, 어떤 위험/기회가 있는지, 업계 전체에 어떤
신호인지)여야 합니다.

**단발성 사실과 인사이트 판단**: 입력이 특정 산업·시장·전략과 연결되는 구조적 함의가 없는
단발성 사실(개별 사건·사고, 확정 안 된 루머, 연예인 개인사)이라면 insights를 빈 배열로 두고
no_strong_insight를 true로 표시하세요. 기업 투자·M&A·정책·소송처럼 구조적 함의로 이어질 수
있는 사건이면 인사이트를 시도하되, 위 정확성 규칙을 반드시 지키세요. 판단이 정말 애매하면
무리해서 인사이트를 만들기보다 no_strong_insight를 선택하는 것이 안전합니다.

근거가 충분하면 인사이트를 2~5개 도출하고, 각 인사이트에는 근거가 된 기사의 source_url을
반드시 포함하세요. 출력은 반드시 JSON이어야 합니다.
```

## 4. 같은 기사를 3라운드에 걸쳐 추적 — Goldman Sachs AI 투자 전망 기사

정답(gold): `no_strong_insight: false`, 인사이트 3개(시장_신호/선행지표/이해관계자_영향).

**Round 1** — 생성 자체가 `max_new_tokens=400`에서 잘려 파싱 실패(인프라 문제, 프롬프트와 무관).

**Round 2** — 판정은 맞았지만(`false`) 숫자를 잘못 베낌:
```json
{"facts": ["... 2028년까지 14%의 글로벌 GDP에 달할 것이라고 전망했다."],
 "insights": [{"claim": "... 업계 전체에 얼마나 큰 영향을 미칠지 평가하는 데 있어 신호가 됨",
               "confidence": "medium", ...}]}
```
Judge: `grounded=false` — "정답은 1.4%인데 모델은 14%로 잘못 표기, 인사이트도 근거 없는 해석을
추가함."

**Round 3** — 숫자는 정확히 고쳐졌지만(`1.4%`) 판정 자체를 놓침:
```json
{"facts": ["... 2028년까지 1.4%의 글로벌 GDP에 달할 것이라고 전망했다."],
 "insights": [], "no_strong_insight": true}
```
Judge: `classification_match=false` — "구체적 수치(1조 달러, GDP 1.4%)는 통찰을 도출할 충분한
근거를 제공하는데도, 모델은 이를 놓쳤다."

이 한 사례가 이번 실험의 핵심 긴장을 정확히 보여준다: **"숫자를 정확히 베껴라"는 규칙을
강화하자 정확도는 올라갔지만, 동시에 넣은 "애매하면 안전하게 no_strong_insight를 선택하라"는
말이 모델을 다시 소극적으로 만들었다.**

## 5. 결론

1. **3라운드 프롬프트 개선 루프는 "더 정교한 지시를 추가할수록 좋아진다"는 가정을 반증했다.**
   각 라운드가 서로 다른 실패 모드 사이를 오갔을 뿐, 세 지표(판정 정확도·근거충실성·품질)를
   동시에 개선한 라운드는 없었다. 굳이 하나를 고른다면 **R1(베이스라인)이 종합적으로 가장
   균형 잡힌 결과**였다 — 특별한 수정 없이도 이미 나쁘지 않았다는 뜻이기도 하다.
2. **"애매하면 안전한 선택(no_strong_insight)을 하라"는 지시는, 학습 데이터의 클래스 불균형이
   만들었던 것과 똑같은 붕괴를 프롬프트 레벨에서도 재현했다** (R3에서 insight-보유 사례 8건 중
   7건을 no_strong_insight로 잘못 판정). 데이터 불균형이든 프롬프트의 "안전 우선" 문구든,
   이 모델(1.7B, LoRA r=8)은 같은 지름길로 수렴하는 경향이 있다는 것을 두 가지 다른 경로로
   확인한 셈이다.
3. **숫자 그대로 인용 규칙은 실제로 작동했다** — Round 3에서 Goldman Sachs 사례의 "1.4%→14%"
   오류가 고쳐진 것처럼, 명시적으로 요구하면 이 작은 모델도 정확한 숫자 복사는 지킬 수 있다.
   다만 이 규칙 하나만으로는 판정 정확도까지 같이 끌어올리지 못했다.
4. **다음에 시도해볼 것**: 세 프롬프트를 섞기보다(안전 문구 없이 정확성 규칙만 유지) 단독으로
   A/B 검증하고, 표본을 15건보다 늘려 라운드 간 차이가 노이즈인지 실제 효과인지 통계적으로
   확인해야 한다. n=15는 방향을 보는 데는 유용하지만 "R3가 R1보다 나쁘다"를 확정하기엔 작다.

## 6. 표본 확대 재검증 — 베이스라인(R1) 프롬프트를 held-out 전체 28건에

3라운드 중 종합적으로 가장 균형 잡혔던 R1(베이스라인) 프롬프트를, 15건 부분집합이 아니라
`insight_val.jsonl` **전체 28건**(생성 실패 방지를 위해 `max_new_tokens=700`으로 상향)에 다시
돌려 최종 숫자를 뽑았다.

| 항목 | n=15 부분집합 (R1) | n=28 전체 (최종) |
| --- | --- | --- |
| 생성 실패 | 4/15 (max_new_tokens=400) | **0/28** (max_new_tokens=700) |
| classification_match_rate | 0.909 (10/11) | **0.857** (24/28) |
| grounded_rate | 0.636 (7/11) | 0.571 (16/28) |
| avg_insight_quality | 51.7 (n=3) | 45.0 (n=9) |

**혼동행렬(n=28)**:

| | 실제 insight 있음 | 실제 no_strong_insight |
